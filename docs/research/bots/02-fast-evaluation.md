# Fast hand evaluation and equity for a 6-max Hold’em bot

The target is **10,000 decisions/s/core**, which allows **100 µs of CPU time per decision on average**. Use a compact OMPEval-style additive hash as the primary evaluator, precompute preflop equity, enumerate heads-up rivers, and cap online flop and multiway equity sampling. Keep a two-word rank-mask evaluator as a small reference implementation and as a viable first release if the policy rarely needs live equity.

On Node 24.22.2 / V8 13.6 on an Apple M5 Pro, the additive hash evaluated a random seven-card hand in **8 ns**, scanned a fixed heads-up river in **1.8–1.9 µs**, and sampled a uniform flop in **29 ns/trial heads-up** or **84 ns/trial six-way** on one fixture. Two Plus Two scanned the same river in **0.89 µs** and used **124 MiB**. Choose based on the full decision path and target device. The measurements below cover kernels, and the end-to-end decision and simulation rates remain to be measured.

### Recommended hot path

Use card IDs `0..51` with `rank = card >> 2` and `suit = card & 3`. A hand state has a rank key and packed suit counts that are **added**, plus two 26-bit words of suit-presence masks that are **ORed**. Cache these contributions for the board, the hero pair, and frequently used opponent pairs. Add the suit-counter bias exactly once when constructing the partial board. Cards must be distinct, with validation at the boundary.

~~~ts
// Each array is built once. These are scalar values in the hot loop.
rankKey[c] = rankMultiplier[c >> 2]
suitKey[c] = 1 << (4 * (c & 3))
x[c] = (c & 3) < 2 ? 1 << (13 * (c & 1) + (c >> 2)) : 0
y[c] = (c & 3) >= 2 ? 1 << (13 * (c & 1) + (c >> 2)) : 0

// Board state starts from x=0, y=0, key=0, suits=0x3333.
// On each new board card, OR x/y and add key/suits.
// Hole pair contributions have zero suit-count bias.
function score(key, suits, x, y) {
  const flushFlags = suits & 0x8888
  if (!flushFlags) return nonFlush[key + rowOffset[key >>> 12]]

  const suit = (31 - Math.clz32(flushFlags)) >>> 2
  const suitedRanks = ((suit < 2 ? x : y) >>> (13 * (suit & 1))) & 8191
  return flush[suitedRanks]
}

const strength = score(
  boardKey + holeKey, boardSuits + holeSuits,
  boardX | holeX, boardY | holeY,
)
~~~

Use signed `Int32Array` for the row offsets or apply explicit unsigned wrap to the upstream offsets. Keep `Uint16Array` scores with higher values stronger. With at most seven cards, a flush can take the early path because there cannot also be a full house or four of a kind. The 13-bit mask scorer can derive the rank masks for one-or-more through four-of-a-kind with ORs and intersections. Its score orders category, made-hand ranks, then kickers. Handle the A–2–3–4–5 straight, two triplets for a full house, and three pairs with the correct kicker. Use the same comparison convention across streets. [OMPEval rank keys and flush handling](https://github.com/zekyll/OMPEval/tree/master/omp), [HenryRLee rank hashing](https://github.com/HenryRLee/PokerHandEvaluator/blob/develop/Documentation/Algorithm.md).

## 2. Equity under a decision budget

**Equity is expected pot share.** A sample scores `0` on a loss or `1/k` if hero is one of `k` winners. The figures here use one contested pot. A simulator with side pots must determine eligibility and split each pot separately. A decision model can combine showdown equity with fold probability, payoff and future betting separately.

### Preflop

- **169 types** are 13 pairs, 78 suited and 78 offsuit. Each represents 6, 4 or 12 physical combos, respectively. Use a **169 × 5** lookup against one through five uniformly random opponents. Build one-opponent values from exact counts. Exact multiway means enumerating disjoint opponent holdings and boards or using an equivalent combinatorial method. Validate provenance before labeling columns exact. A compact Monte Carlo table with a declared sample count is inexpensive and suits the latency target. [Exact heads-up data and multiway simulation example](https://github.com/dafmontenegro/holdem-preflop-equity).
- For a fixed hero, the raw labeled-opponent deal count is `C(50,5) × C(45,2) × C(43,2) × …`. This starts at **2.10 billion** heads-up, rises to **1.89 trillion** with two opponents and **7.66 × 10²⁰** with five. Interchangeable uniform seats allow division by `n!`. A fixed board turns the question into counting disjoint two-card edges by showdown outcome. Exact subset or matching methods can exploit that structure, but naive enumeration is impractical for the full 6-max table. Heads-up equity raised to a power also loses the shared-board correlation and card blockers. [Exact and sampled workload examples](https://github.com/dafmontenegro/holdem-preflop-equity).
- **Heads-up versus known ranges** can be exact from precomputed suit-aware matchup equity. Canonicalize the joint hero/villain suits, or canonicalize hero once and use a dense hero-row lookup. With a model that assigns one common weight per combo of each class, a class-pair matrix suffices if you weight every cell by the number of legal disjoint combos. Some offsuit matchups change equity depending on which suits coincide. Use suit-aware rows for arbitrary per-combo weights. For several weighted opponents, use joint sampling or a precomputed table for that specific collection of range and seat models. An extra dead card changes the distribution of boards and needs its own conditioning. [Suit-pattern matchup enumeration](https://mathematrucker.com/poker/matchups.php), [exact class aggregation](https://georgelipoker.com/equity).

### Postflop exact and sampled paths

| Street, heads-up | Current HS opponent combos | Terminal joint states with fixed hero | Online choice |
| --- | ---: | ---: | --- |
| Flop | C(47,2) = 1,081 | C(47,2) × C(45,2) = 1,070,190 | Exact current HS if needed. Sample terminal equity or read a cached feature. |
| Turn | C(46,2) = 1,035 | 46 × C(45,2) = 45,540 | Exact for sparse ranges or offline. Sample wide ranges on a tight deadline. |
| River | C(45,2) = 990 | 990 | Exact heads-up. Sample broad multiway ranges. |

These counts assume no extra dead cards. The cheapest exact turn loop often puts the river card outside, calculates hero once per runout, then iterates the legal opponent combos. That measured **84 µs** with the additive hash or **230 µs** with suit masks for a full uniform turn scan on one fixture. Range weights and action logic take extra time. Narrow turn ranges can use the opposite loop order with about `44 × legalCombos` showdowns. Flop-to-river pairs are unordered for final equity, and street order matters for one-street potential or policy rollout. Precompute the board fragments and hero scores before scanning a large range. [Poki’s HS and hand potential algorithms](https://poker.cs.ualberta.ca/publications/AIJ02.pdf).

- **HS** is current made-hand strength versus the legal range, with ties worth half heads-up. Rank the best five of the available 5–7 cards and sum weighted wins and ties. It ignores future cards.
- **Hand potential** tabulates transitions among ahead, tied and behind from now to a chosen horizon. Increment a flat nine-element counter by the sample or enumeration weight. Positive and negative potential use the corresponding transitions, including half weights for ties. Normalize by row masses measured at the same terminal-trial granularity. An empty denominator has no transition contribution.
- **EHS** in the full Poki formulation is `HS × (1 − NPot) + (1 − HS) × PPot`. With consistent tie weights and the same terminal distribution, the transition matrix also gives showdown equity directly from its finish columns. Poki’s positive-only feature `HS + (1 − HS) × PPot` is a separate betting feature. If the goal is terminal equity, skip computing HS and the transition matrix unless the policy uses them. [Billings, Papp and colleagues](https://poker.cs.ualberta.ca/publications/AIJ02.pdf).
- **EHS² / HS2 for bucketing** means `E_b[h(b)^2]`, where `h(b)` is heads-up showdown equity conditional on the completed board `b`. It captures runout dispersion via `E[h²] − E[h]²`. Compute a conditional opponent sweep for each board, or estimate the square using the product of two independent opponent samples conditional on the same board. Squaring a single win/tie/loss sample measures a different moment. Against nonuniform ranges, weight each runout by its remaining legal opponent mass under the joint deal distribution. [Schnizlein’s description of HS2 percentile bucketing](https://poker.cs.ualberta.ca/publications/schnizlein.msc.pdf).

### Monte Carlo sample sizes and error

Draw the missing board and all opponent cards without replacement. Use `Uint8Array` scratch for the selected cards and two 32-bit occupancy words. For uniform ranges, either draw unbiased bounded indices using a partial Fisher–Yates shuffle or use a 6-bit candidate with rejection of values ≥52 and collisions. Reuse the board state per trial, score hero once, and stop evaluating opponents as soon as hero is beaten. If reporting multiple players’ equities or paying side pots, evaluate the players needed for those results.

The half-width is `1.96 × 0.5 / sqrt(N)` using the worst-case variance bound for independent samples in [0,1] and a normal approximation. For validation use sample variance or a suitable interval, especially for rare outcomes. At **100 µs of pure kernel**, this fixture fits about **3,400 heads-up** or **1,180 six-way** trials. Suit masks took **41–44 ns** and **108–115 ns**, respectively, on the same workload. The benchmark had a fixed flop and known hero, uniform opponents, a small seeded xorshift and early loss exits. Tougher cases include boards where hero usually survives all five opponents, sparse colliding ranges, and mobile browsers. Enable a cheap first pass and spend extra samples near meaningful action boundaries or on high-value decisions. For confidence-based adaptive stopping, use an interval that accounts for repeated looks, or keep the first pass as a heuristic and report fixed-sample intervals separately. A published M1 Node 20 call into Wasm took **2.92 ms heads-up** and **7.24 ms six-way** for 10,000 preflop trials. The API, street, and machine differ from the local kernel. [Published benchmark and workload](https://github.com/pokerinfra/poker-eval#equity).

### Weighted combos and isomorphism

- Give all **1,326** two-card combos stable IDs. For sorted cards `a < b`, use `id = a × (103 − a) / 2 + (b − a − 1)`. Store two card IDs, two occupancy words, class ID, evaluator fragments and per-range nonnegative weights in flat arrays. Compact to nonzero legal combos once per fixed board or model change. Reuse compact vectors across decisions where the actual range and blockers match.
- **Fixed hero vs one range:** filter against hero and board, accumulate `sum(weight × payoff) / sum(weight)`. Heads-up preflop uses a suit-aware matrix and at most 1,225 possible opponents. On river, pre-score hero and each legal combo. For sampled postflop, build a cumulative-weight array or alias table once per stable range. With alias tables, draw independently from each seat’s proposal and reject the **whole tuple** on collisions. That samples weights proportional to the product conditioned on legality. Resampling later seats only can bias earlier seats by ignoring their differing compatible mass. For two narrow or overlapping ranges, precompute each hero combo’s compatible opponent weight, sample hero proportional to `heroWeight × compatibleMass`, then draw opponent conditionally. For more seats with low acceptance, precompute compatible groups, use a validated conditional sampler, or return a bounded-cost approximation. Give empty or incompatible ranges an explicit result. [Poki range weighting](https://poker.cs.ualberta.ca/publications/AIJ02.pdf), [OMPEval equity design](https://github.com/zekyll/OMPEval#about-the-algorithms-used).
- **Range vs range:** heads-up preflop exhaustive aggregation is at most **1,624,350 ordered legal combo pairs** before suit reduction. Precompute `heroRowDotRange` for recurring villain models, then sum across hero weights outside the action loop. On a fixed river, rank each combo once and process tied score groups in order. Keep opponent mass globally and per card for ranks lower than the group and for ranks equal to the group. For hero cards `a,b`, subtract masses containing either card, adding back their intersection when present. This gives compatible lower and tie mass with a few scalar operations per combo. Use the same exclusion for the denominator and aggregate with hero weights. On flop or turn, reuse this sweep on a cheap set of sampled runouts, weighting by the compatible joint mass of each runout if sampling boards uniformly. Alternatively draw legal joint hole-card tuples first and then sample the remaining board. Avoid a general all-pairs scan inside each decision.
- **Suit canonicalization:** rename all suits jointly, preserving hero/villain roles and the flop/turn/river groups required by the feature. For generation, a simple reference key is the minimum encoding over 24 suit permutations, sorting only inside unordered groups. Retain multiplicity when aggregating orbits. Use a dense indexer such as Waugh’s for frequent lookup, and canonicalize once per state. For exact enumeration within a fixed state, collapse only symmetries that also preserve hero, board, dead cards, and the weighted ranges, or transform the ranges with the card labels before lookup. [Waugh’s paper and state counts](https://www.cs.cmu.edu/~waugh/publications/isomorphism13.pdf), [reference indexer](https://github.com/kdub0/hand-isomorphism).

### Generate offline with a Node script

1. **Evaluator:** build the mask LUTs by walking `0..8191`. For the additive evaluator, pin upstream rank multipliers and row offsets. Enumerate all rank multisets of sizes 5–7 with multiplicity ≤4. Assign valid suits cyclically to avoid a flush while deriving the nonflush score from the reference. Separately score every flush rank mask of size 5–7. Compress the distinct scores to ascending 16-bit IDs. Assert that reused hash slots give the same score. Local generation of the compact score tables took **13–15 ms**. Check bundled-table licenses and retain attribution when reusing upstream constants or datasets.
2. **Exact preflop heads-up:** enumerate representative disjoint hero/villain hands modulo joint suit renaming and swapping. For each representative, walk the **1,712,304** boards from the remaining 48 cards, reusing board prefixes. Accumulate integer wins and ties. Store orientation and aggregate into class cells using legal combo multiplicities. **47,008 × 1,712,304 ≈ 80.5 billion** board comparisons before further board orbit savings or shared work. At an illustrative **5–20M complete boards/s/core**, that is **1.1–4.5 core-hours**. One published Node/Wasm exact matchup took **216 ms** (~7.9M boards/s) on M1. The whole generation time is a projection. For quick generation, import a verified exact dataset where the license fits, or distribute representative batches over workers and checkpoint by index. [Suit-aware counts](https://mathematrucker.com/poker/matchups.php), [exact-match benchmark](https://github.com/pokerinfra/poker-eval#equity).
3. **Random multiway and static ranges:** shard the 169 hero classes over workers. For the one-through-five uniform table, deal one five-opponent trial, walk opponents in a fixed order, and accumulate the hero pot share at each prefix. Every prefix has the right marginal distribution. `100,000` trials per hero class take **16.9M deals** and give a worst-case normal half-width of approximately **±0.31 pp** per entry. At **0.15–0.40 µs/deal** as a planning assumption for generation, that is **2.5–6.8 core-seconds** for the kernel, plus setup and output. Narrow weighted profiles need their own work estimates based on acceptance. Compare the sampled HU column against the exact column and use exact values in the shipped table.
4. **Flop/turn features:** enumerate canonical states or sample states in proportion to their intended training distribution. Compute selected HS, EHS², equity or texture features, fit bucket boundaries or centroids offline, and write IDs at canonical indices if storing a dense map. At **1,024 trials × 1.29M flop states ≈ 1.32B trials**, an illustrative **50–200 ns/trial** is **66–264 core-seconds** for the sampling kernel. Index construction, weighted sampling and bucketing add to that. Exact flop equity needs about **1.38 trillion joint outcomes** if separately enumerated for every canonical state, so exhaustively generating exact features merits board-first reuse and a separate throughput study. [Street indexing](https://www.cs.cmu.edu/~waugh/publications/isomorphism13.pdf), [bucketing examples](https://poker.cs.ualberta.ca/publications/schnizlein.msc.pdf).
5. **Verify:** compare the scorer with a separate five-card reference plus best-of-21, including wheels, straight flushes, double trips, kickers and ties. Exhaustive seven-card category counts cover **133,784,560** inputs. Verify suit permutation and card order invariance. For equity, check mirror matchups, all-player shares summing to one, blocker handling, and weighted sampling against enumeration on small fixtures. When averaging starting-hand values against uniform opponents, weight types by their physical combo counts and expect an overall mean of `1/(n+1)`.

## 4. V8 and worker performance

- **Keep the hot path numeric.** Use `Uint8Array` for the deck and card IDs, `Uint16Array` for scores, `Int32Array` or `Uint32Array` for masks and offsets, `Float32Array` for range weights if precision allows, and JS numbers or `Float64Array` for accumulators. Typed arrays give a predictable layout, cheap binary I/O and no holes. A small fixed set of local scalars often beats combining object states. Construct stable object shapes for the simulator and keep argument types consistent. Inline small numeric functions if profiling identifies call overhead. Hoist bounds/duplicate validation and conversions out of the loop. [V8 elements kinds](https://v8.dev/blog/elements-kinds), [V8 fast properties](https://v8.dev/blog/fast-properties).
- **Allocate scratch once.** Preallocate per-worker decks, actions, ranges and output buffers. Avoid building a new object, tuple, iterator, closure, or `Map` per showdown or sample. Long-lived closures and maps outside the kernel are fine. Separate parsing and diagnostics from numeric calls. Benchmarks should consume a checksum so the work remains observable.
- **Use integer coercions where they carry meaning.** Bitwise JS operands are 32-bit. `>>> 0` yields an unsigned word, `| 0` a signed one, and `Math.imul` gives the low 32 bits of an integer product. One `1 << card` cannot encode a 52-card deck. Avoid blanket coercion and preserve exact wider sums as `Number` up to its safe-integer range. Use larger-than-32-bit counters for offline totals that need them. Benchmark before assuming forced coercion helps the JIT.
- **Use a seeded integer PRNG.** Xorshift32 is tiny and was used for these timing fixtures, with a nonzero state. Its short, linear stream makes it a weak default for large training runs. Mulberry32 is a convenient 32-bit-state option with `Math.imul` mixing. Prefer sfc32 for repeatable multiworker simulation, with independent per-shard seeds, several warm-up rounds, a pinned algorithm and a strong expansion of the root seed into its state. Measure all candidates in the deal/sampling loop if RNG time matters. Use unbiased bounded draws, such as rejection above the largest multiple of the bound below 2³², or mask-and-reject. Derive per-shard seeds from stable shard IDs so changing worker counts can preserve reproducibility. [Marsaglia’s xorshift paper](https://www.jstatsoft.org/article/view/v008i14), [32-bit JS PRNG implementations](https://github.com/bryc/code/blob/master/jshash/PRNGs.md), [sfc32 design notes and implementation](https://pracrand.sourceforge.net/).
- **Parallelize batches of hands.** Use a persistent Node `worker_threads` pool or Web Workers. Shard whole hands, or whole tables when stacks and opponent models carry over between hands. Give each worker its own mutable state and send an aggregate per shard. Start with thousands of hands per task, then tune for utilization and load balance. Run self-play on separate workers from latency-sensitive inference and measure both together on the actual core allocation. Test the performance and efficiency cores as well as browser targets, since a single-thread macOS benchmark did not pin a physical core. [Node 24 worker documentation](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html).
- **Send small messages or transfer buffers.** `structuredClone` copies ordinary typed-array backing data unless its buffer is transferred. In local ten-copy microbenchmarks, a 125,000-byte array averaged **21–34 µs/copy**, and a hot 129,951,336-byte array averaged **7.5–9.1 ms/copy**. These are in-process measurements and exclude worker round-trip time. For single ownership, transfer a standalone `ArrayBuffer` and account for sender detachment. In Node, avoid assuming pooled `Buffer` memory can be transferred cheaply. Share read-only evaluator tables via `SharedArrayBuffer` where useful. Browser sharing requires cross-origin isolation in normal deployments. Compact tables can also be copied once at worker startup. [Node transfer semantics](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#portpostmessagevalue-transferlist), [browser transferables](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects), [browser shared memory](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer).

## 5. Integration and performance budget

| Operation | Suggested default | Expected CPU cost |
| --- | --- | ---: |
| Preflop, uniform opponent count or known static model | Indexed U16 fetch | Target **<1 µs**, including class index. Estimate. |
| Preflop, dynamic heads-up model | Dot product over legal combos with a suit-aware row. Memoize stable profiles. | Plan **single-digit to low tens of µs** once the row and range are materialized. Benchmark with the actual weights and cache behavior. |
| Flop, heads-up | 256–512 uniform trials or a cached model feature | **7–15 µs** fixture kernel. Weighted sampling and policy consume additional time. |
| Flop, up to five opponents | Start at 128–256 trials. Refine when the action merits it. | **11–22 µs** for the six-way fixture. Budget from measured acceptance and all-opponents-evaluated cases. |
| Turn, heads-up | Scan sparse ranges exactly. Sample wide ranges on the fast path. | **84 µs** for one full uniform fixture with the compact hash. |
| River, heads-up | Exact over the legal range with a cached board | **1.8–1.9 µs** for the 990-combo uniform compact-hash fixture. |
| River, broad multiway | Sample legal disjoint tuples with board and hero score cached | Measure online. The flop sample timings provide a reference, with no future board to draw. |
| Showdown within self-play | Reuse one board state for every eligible player | Mask benchmark **~0.10 µs/hand** for a uniform 17-card partial shuffle and six hand scores, about **5 ms for 50,000 hands** for this kernel. Full simulation adds betting, state transitions, decisions and payout. |

A practical first budget is **up to 25 µs for equity features**, **up to 50 µs for policy/action and state**, and **25 µs of headroom**. These are allocations for measurement. If there are on average 12 policy decisions per hand, 50,000 hands take 600,000 decisions, or **60 core-seconds** at the minimum throughput and **12 core-seconds** at 20 µs/decision, before simulator overhead. Use fast, deterministic table-based policies for bulk training where their quality suffices, and reserve more expensive sampling or rollout for narrower batches.

Before claiming the target, run **50,000+ whole hands** with the real action policy and realistic range distributions. Measure sustained decisions/s per worker, hands/s, cold startup, p50/p95/p99 decision latency, slow-path frequency, and resident memory, with self-play both off and active. Use the intended production browser and Node 24. Include dry boards where hero usually survives, flush-heavy boards, broad and tight ranges, and runs that defeat cache reuse. Compare strategy agreement with a larger offline equity sample. A faster kernel is valuable when it preserves action quality at the selected budget.
